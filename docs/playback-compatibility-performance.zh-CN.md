# 格式兼容性与播放性能参考

[English](playback-compatibility-performance.md) | 简体中文

更新日期：2026-10-31。实测数据截至：2026-10-30。当前代码基线：`781e81e`。

本文按封装、编码和播放路径整理能力、实测与限制，供后续开发和回归参考。所有真实媒体案例均改用匿名编号，不记录媒体名称、资料库名称、服务器地址、文件路径、项目 ID 或访问凭据。

设置与转码策略见[播放与解码支持](playback.zh-CN.md)。本文的实测结果主要来自 Plex 原文件播放；不能直接推广为 Jellyfin / Emby、所有设备或所有同编码文件的验收结果。

## 1. 如何理解“支持”

| 标记 | 含义 |
| --- | --- |
| 已接入 | 代码存在解析、解码或渲染路径；是否可用仍取决于设备和文件 |
| 样本通过 | 指定设备、格式组合及短片段观察通过；不代表全片或全部同类文件通过 |
| 有条件 | 需要设置开关、指定硬件能力或兼容回退，可能有画质限制 |
| 待验证 | 未获得足够实播证据，不能据此写为支持或不支持 |

直接播放表示客户端处理原始媒体，不使用服务端转码。本地 FFmpeg 软解、PCM 下混、RM 解封装、字幕渲染和 HEVC 兼容播放仍属于本地处理。视频硬解与音频硬解也可能分别采用不同路径。

验收应分开记录：能否起播、持续推进、实际画面、颜色与动态范围、音频输出链路、实际听感、字幕显示，以及跳转后恢复。READY 不等于已经显示首帧，也不证明随后不会重缓冲。

## 2. 环境与覆盖范围

- 产品最低 Android API 21；Media3 固定 1.8.0，打包 ARM32 / ARM64。
- 主要实播环境：一台 Android 8 / API 26、约 1.6 GiB 可见系统内存的投影仪，应用使用 ARM32 进程；显示端不支持 HDR / Dolby Vision。
- 部分解码与生命周期测试另在 ARM64 环境验证；不等于 ARM64 全界面、全格式实播验收。
- 直接播放测试使用原画质，关闭服务端转码与字幕烧录；匹配的服务器会话采样未见转码会话。这是抽样证据，不是全程抓包。
- 初轮覆盖 51 个格式组合，后续对异常格式修复并补充同类型样本；未逐个播放整个媒体库。初轮失败数与计时不能当作当前版本统计。
- 音频主要核验解码器、PCM / AudioTrack 输出和时钟推进，实际扬声器听感、长时间音画同步、Atmos / DTS:X 输出仍待现场验收。

当前设备测试中，HDR / DV 偏暗或偏色单独记为“颜色未正确还原”，不计为解码起播失败。这个口径不表示画质正确，也不能用于有正确 HDR / DV 输出要求的验收。

## 3. 封装支持

| 封装 | 当前路径 | 验证与边界 |
| --- | --- | --- |
| MKV / Matroska | Media3 + libass 集成；附加索引探测与 PGS 快照输出 | 多类样本实播；链式 SeekHead、混合视频/字幕 Cues 已修复 |
| MP4 / M4V / MOV | Media3 解封装 | MP4 有实播样本；其他扩展名不能视为逐项实测通过 |
| RM / RMVB | FFmpeg 本地增量解封装，经现有 DataSource 读取 | RV40 + AAC、RV40 + Cook 实播通过；不预先整集下载 |
| WebM、TS / MPEG-TS、FLV、AVI、OGG、3GP | 已列入封装能力白名单，使用播放器现有路径 | 本轮没有覆盖每种封装，仍需目标设备验证 |
| MP3、AAC、FLAC、M4A | 已列入封装能力白名单 | 不代表本轮完成独立音频文件的全面验收 |

扩展名、可识别容器及可实际解码是三件事；损坏文件、异常轨道、缺失参数和服务器返回错误仍可能导致失败。

MKV 索引处理优先复用可用的视频同步点；没有可用索引时保留按 Cluster 查找的回退。未知长度、超探测预算、损坏索引及多视频轨仍有边界，不能保证任意落点都能立即恢复。

## 4. 视频编码与本地软解

| 编码 / 类型 | 当前路径 | 当前证据或限制 |
| --- | --- | --- |
| H.264 / AVC 8-bit | 平台解码器优先 | 多类 SD / HD 样本通过，普通 AVC 对照仍使用硬解 |
| HEVC / H.265 Main、Main10 | 平台解码器 | 1080p / 4K 样本通过；分辨率、帧率、码率与 profile 仍受设备约束 |
| H.264 High10 | 开启视频软解后可使用本地 FFmpeg | 当前投影仪硬解失败；720×496 SDR 同类型样本软解通过，不代表所有 1080p High10 都流畅 |
| RV40 | 平台 `video/realvideo` 优先；允许时可本地软解 | 当前设备的 `OMX.MS.RV.Decoder` 实播通过；其他设备不保证存在此解码器 |
| MPEG-2 | 已接入平台解码路径 | 初轮有样本；未做该编码的全面压力测试 |
| VP8、VP9、AV1、MPEG-4、VC-1 | 已接入能力识别，依赖可用平台解码器 | 本轮缺少足够实播覆盖；当前视频软解回退不覆盖这些编码 |
| 其他未映射编码 | 无通用保证 | 按能力与用户允许的转码策略处理 |

“设置 → 兼容性 → 允许视频软解”默认关闭。开启后仍优先使用可用硬解，仅为 H.264 / RV40 的符合条件视频提供软件尝试：

- 已知且有效的尺寸，最长边 ≤ 1920、短边 ≤ 1080，包含 1920×1080；不是严格“低于 1080p”。
- SDR；HDR、不明尺寸、超限视频不进入该回退。
- 原始压缩视频在本机解码，不请求服务器重新编码。
- 这是保护上限，不是实时性能承诺；低分辨率 High10 成功不能推出 1080p 高帧率、高码率也成功。

Cook 音频软解独立于这个开关。关闭视频软解不会关闭 FFmpeg 音频解码。

## 5. HDR 与 Dolby Vision

| 类型 | 当前行为 | 本轮验证边界 |
| --- | --- | --- |
| HDR10 / HDR10+ / HLG | 依赖解码器、系统输出链及显示端；客户端不做色调映射 | 非 HDR 投影仪出画面不代表正确 HDR 输出；本轮未完成 HLG / HDR10+ 的完整输出验收 |
| DV P5 | 优先原生 DV；无可用 DV 解码器或原生路径失败时尝试普通 HEVC 兼容播放 | 4K 样本能出画面、音视频推进；仍可能偏绿 / 偏粉，不是正确 HDR10 / SDR 转换 |
| DV P7 | 优先原生 DV，失败后尝试 HEVC HDR10 基础层 | 样本基础层通过；未证明原生 DV 或增强层完整还原 |
| DV P8 | 可由可用解码器播放兼容基础层；具体 HDR10 / HLG 属性随 profile 变体而定 | 样本实际使用普通 HEVC；不能写成原生 DV 输出通过 |

原生 DV 无首帧时，播放器会在等待阈值及缓冲条件满足后尝试 HEVC 回退，并按 profile 记录本机失败结果。首次检测可能明显慢于后续兼容起播；不同设备需要重新验证。

P5 没有 HDR10 兼容层，HEVC 兼容路径仅解决“出画面”。更换设备后，正确色彩仍要求播放器解码路径、盒子、显示端及输出链共同支持对应 DV profile，不能只看电视上有“杜比”标识。

“电视支持 HDR”关闭且允许服务端转码时，HDR 源会触发转 SDR 策略；禁止服务端转码时并不会凭空获得本地色调映射。

## 6. 音频格式与输出

| 音频 | 当前路径 | 已观察到的范围与限制 |
| --- | --- | --- |
| AAC LC / HE-AAC、AC3、EAC3 | 可用平台解码器优先，必要时 FFmpeg | 多种声道数组合的输出链路有样本；不等于全部 profile 验收 |
| DTS、DTS-HD MA、DTS Express | 平台或 FFmpeg 解码为 PCM | 有输出样本；Express 的源声道数与解码报告曾有差异，未确认声道忠实性 |
| TrueHD | 平台能力与 FFmpeg 路径 | 2ch、5.1、7.1 实播；特定流零 PCM 的初始化/重置问题已修复 |
| Cook | 明确使用 FFmpeg | 双声道 RM 样本通过；厂商硬解虽可枚举，但标准配置未打通，不用作产品依赖 |
| FLAC、Opus、PCM | 平台或已有本地音频路径 | 有格式样本；PCM 曾观察到 24-bit → 16-bit、多声道 → 立体声输出 |
| MP3、MP2、Vorbis、ALAC | 已映射能力，依赖平台 / FFmpeg 实际支持 | 本轮无充分逐格式实播覆盖 |

默认关闭音频直通，将解码后的多声道 PCM 下混为立体声，以适配电视和投影仪内置扬声器；这不等于保留原声道布局，也不证明 Atmos / DTS:X 对象音频还原。

开启直通后，可用格式由系统 HDMI 能力和接收端共同决定，直通音轨固定 1×。本轮没有完成接功放后的全格式直通、声道定位与听感验证。

## 7. 字幕格式

| 字幕 | 当前路径 | 已验证与限制 |
| --- | --- | --- |
| SRT / SubRip | 本地文本解析；外挂旧编码兼容路径 | 旧编码乱码修复样本已回归；不能保证所有未知编码自动识别正确 |
| ASS / SSA | libass | 内封 / 外挂路径已接入；双语对白及特效样本通过，不代表所有字体与动画都穷举 |
| 内封 PGS（MKV） | Loader 生成压缩状态快照，独立 worker 按字幕时钟解码和渲染 | 多对象、窗口/裁切、调色板增量、状态复用；暂停切轨、快进快退与逐像素对照通过 |
| 外挂 SUP / PGS | 自定义 SUP 解析、时间戳定位与 seek 状态预热 | 对白和画面内翻译特效样本通过；未使用本次内封 PGS 快照路径 |
| WebVTT | 已接入本地文本路径 | 当前样本覆盖不足 |
| 内封 VobSub / DVD、mov_text / tx3g | 已列入本地字幕能力 | 初轮内封 VobSub、mov_text 有字幕截图通过；不代表全部样式及文件通过 |
| 内封 DVB | 已列入本地字幕能力 | 本轮样本覆盖不足；外挂 VobSub / DVB 不在当前外挂字幕能力清单 |

内封 PGS 选择过滤只在可确定单原文件等条件下启用；不能安全对应轨道时保留回退行为。字幕关闭与切轨不应继续生成无用的 PGS Bitmap。

快照历史预算为 **20 秒 / 16 MiB / 2048 条**，时间淘汰保留窗口前的最后一个有效状态；硬字节和条数预算优先，单个合法大样本可保留一条。这避免无限累积，但极密集字幕未必保留足 20 秒。

快照能独立解码已进入 SampleQueue 的字幕状态，却不能补出原文件网络 seek 起点之前未读取的 palette / RLE 对象。跨 epoch 跳转及非零正字幕延迟的全新 seek 仍需专项预滚验证。

## 8. 性能指标口径

| 指标 | 定义 | 不能代表什么 |
| --- | --- | --- |
| plan → READY | 播放方案日志到首次 READY | 不是应用冷启动或精确首帧时间，不保证后续稳定 |
| 启动 → 首帧 | 启动测试到目标视频首帧事件 | 含 Activity、元数据、网络与解码，不能只归因于 codec |
| seek → READY | 提交目标到恢复 READY | 不等于首帧显示或首两帧连续输出间隔 |
| 首两帧间隔 | 新目标的前两个有效视频输出帧间隔 | 不含 seek 之前的加载，不能与 seek → READY 相减代替总耗时 |
| 重缓冲 | 已起播后重新进入 BUFFERING 到 READY | 与有缓冲却停画是两类故障 |
| dropped | 日志累计丢帧计数 | 0 不等于已经逐帧证明观感完美 |
| CPU / PSS | 指定窗口线程 CPU / 指定时刻进程内存 | 不是整机峰值、长期平均或所有资源的固定成本 |

下列性能均为指定格式短片段观测，不是跨设备排行榜或全片统计分位数。硬件、网络、关键帧间隔、缓存、字体、字幕密度和温控都会影响结果。

## 9. 匿名性能样本

### 9.1 密集动画 PGS：样本 P-01

组合：1080p H.264 + EAC3 7.1 + MKV 内封双语特效 PGS；同一目标位置起播，每轮观察 75 秒。

| 阶段 | plan → READY | 起播后重缓冲 | 日志累计丢帧 |
| --- | --- | --- | --- |
| PNG 路径基线 `5a6d783` | 17.111 s | 1 次，7.373 s | 未用于本轮比较 |
| 快照方案首次测试 | 10.731 s | 无 | 0 |
| 快照方案重复测试 | 8.000 s | 无 | 0 |
| 最终版本 `781e81e` 对应实现 | 8.012 s | 无 | 0 |
| 关闭字幕对照 | 6.853 s | 无 | 0 |

前两轮快照测试使用较小的历史预算；最终版为兼容字幕延迟调节扩大到上述有界预算。因此内存应以最终版观测为准，不能混用中间方案数据。

- 最终版 PSS 约 **129.6 MiB**，基线约 **107.4 MiB**；CPU 开销改善并不等于内存降低。这是单次同观察窗口末尾采样，非峰值。
- 初始两轮在墙钟 18–32 秒窗口的 Loader CPU：基线 76.3%，快照方案 13.1% / 5.5%；新字幕 worker 8.8% / 5.9%，以单核 100% 计。加载节奏不同，不能直接当作固定加速比或最终版 CPU 指标。
- 交互测试快进 / 快退的 seek → READY 为 **5.534 / 4.260 s**，仍有加载等待。
- 暂停关闭字幕、切另一条 PGS 后仍暂停且字幕刷新正常；恢复后切回原轨通过。

同设备的独立 ARM32 字幕管线探针，不含网络和视频解码：

| 约 25 秒字幕片段，834 个显示集 / 675 个 Bitmap | 耗时 |
| --- | --- |
| 旧 parser + PNG 编码和解码 | 20.677 s |
| 新 Loader 生成压缩快照 | 0.399 s |
| 新快照全部解码 | 2.063 s |

834 个显示集与旧 parser 的像素、几何位置完全一致；打乱快照顺序后独立解码通过。独立进程堆与完整播放器不同，上表不能代替实播起播时间。

### 9.3 MKV 索引、TrueHD 与 DV 兼容

| 匿名场景 | 观察结果 | 解释 |
| --- | --- | --- |
| K-01：11 个 MKV 样本、33 个阶段 | 起播/续播 11 次、固定目标跳转 22 次；新目标首两帧间隔 38–80 ms，首 PTS 偏差 0–37 ms；seek → READY 1.758–5.972 s | 未再触发原“READY、有缓冲但帧输出停滞”的筛查条件；不代表无加载 |
| A-01：特定 TrueHD 2ch 流 | 修复前 PCM 为 0、反复缓冲；修复后同格式独立样本与 5.1 / 7.1 对照持续输出 | 已修复初始化与 reset 的声道布局问题，实际听感待确认 |
| A-01：同流较远目标跳转 | 单次 seek → READY 12.457 s，随后 PCM / 视频继续推进 | 剩余加载性能问题，根因尚未闭合，不再归为零 PCM 卡死 |
| D-01：4K DV P5 首次原生失败后回退 | 启动 → 首帧 17.593 s | 包含原生检测与重开开销，不是单纯解码耗时 |
| D-01 / D-02：已知 HEVC 回退路径 | 启动 → 首帧 4.710 / 6.585 s | 仍有偏色；两个同格式样本均有画面及位置推进 |

K-01 多数样本为隔离索引问题而关闭字幕，不能作为密集字幕性能的证明。索引修复要求从正确前置同步点解码，部分位置的加载时间可能比错误索引时更长；应同时比较加载与恢复后的连续出帧。

## 10. 当前限制与回归优先级

1. DV P5 兼容路径的颜色仍未修正；原生 DV、HDR 正确输出和完整增强层处理需要合适设备另测。
2. 部分 MKV 起播 / seek 仍需数秒加载，特定 TrueHD 样本曾单次达到约 12.5 秒；不能把所有等待都归因于网络或同一根因。
3. PGS 密集动画的已测重缓冲已改善；仍需长时间、全片、跨 epoch seek、非零延迟和极密集字幕压力测试。
4. 视频软解仅有条件开放 H.264 / RV40，1080p 是尺寸上限，不是性能保证。
5. 实际听感、长期音画同步、直通、Atmos / DTS:X、全片字幕同步与多 Part 无缝衔接未全面验收。
6. 未实播的编码、损坏/未知格式样本及索引扫描失败项保持“待验证”，不能计为已确认播放失败，也不能推定支持。

## 11. 验证与维护

当前 PGS 优化交付前，Debug / AndroidTest / Release 构建、4 个 JVM 模块共 65 个测试、主要投影仪 instrumentation 均通过。设备测试包括快照像素对照、输入预算、轨道过滤、sample offset / 附加数据、暂停、seek、EOS、period 边界、worker 合并、过期结果丢弃和 Bitmap 生命周期，并回归 SUP、索引、TrueHD、DV、软件视频与 RM 路径。

./gradlew :core:test :net:test :server-plex:test :server-jellyfin:test

### 2026-11-02 调度与负载优化

本轮借鉴 [blbl 的调度与负载预算策略](https://github.com/cat3399/blbl/tree/cd09bd903e6d0c22f5986580c2105796d8df6471/app/src/main/java/blbl/cat3399/feature/player/danmaku)，保留 AkDanmaku 排布和渲染算法，自行实现适配，未复制 blbl 源码。

- 使用 Ak 的手动模式，由一个串行 worker 与其 Choreographer 调度。暂停／缓冲不连续更新，保留缓存和冻结快照；seek、尺寸变化和异步缓存完成只请求合并后的有限补帧。UI 消费确认提供背压，避免后台提前回收仍在绘制的快照。所有 debug Ak 实例统一使用该模式，不混用自动模式。
- 播放状态／速度仅在变化时提交；仅初始化和时间不连续立即 seek。每秒采样漂移，连续三次超过 300 ms 才纠偏，纠偏冷却 10 秒；暂停不周期纠偏。
- 入引擎前按滑动 500 ms 窗口限流：早期版本普通最多 1 条、压力最多 6 条；当前上限见本节开头，跟随用户数量档位；文字限制为 80 个 Unicode code point，避免截断代理对。后台生成、排序和筛选，实体创建在 worker 执行；窗口结束前 30 秒预备下一窗口，取消或关闭后过期结果不安装。
- 每次更新最多接纳 8 个测量／缓存任务，等待队列上限 64，另有至多 1 个执行中任务。拒绝和取消恢复中间状态，允许后续重试；`rejected` 是拒绝尝试数，包含重试，不是丢弃弹幕数。
- `LumyDanmaku` 每 10 秒输出 update/draw/interval 的累计次数与最近 256 个样本的 p95、max，以及缓存命中、队列深度／峰值／拒绝、工作耗时、Java/native heap 和同步操作计数。update/draw 是线程路径的墙钟耗时，draw 为弹幕子树的 UI 提交路径；interval 是提交间隔，均不是 GPU 耗时或实际呈现 FPS。Heap 也不是 PSS；整机 GPU、GC、PSS、合成和热状态仍需系统工具采样。

定向回归增加了暂停稳定后 2.2 秒 update/draw 计数不增长、paused seek 实际可见 ID 改变后重新静止、心跳不重复 start/seek、时间窗口边界突发、Unicode 长度、缓存队列和取消重试检查。验证命令保持上述 `-e danmaku_only true`。原有线程退出补丁保留，补丁与构建输入见[第三方说明](../third_party/akdanmaku/README.md)。本轮仍只验证小分辨率合成片源，不据此声称低端 4K 已达标。

设置绑定之前的历史末次 API 31 ARM64 TV 模拟器、宿主 GPU 模式回归通过（仍为 1920×1080 UI／320×180 合成 H.264）。各 5 秒单次采样中，普通／压力档的 UI 绘制为 291／248 次，视频丢帧计数均为 0；更新耗时 p95 为 0.88／2.34 ms，弹幕 UI 提交耗时 p95 为 0.26／0.60 ms，提交间隔 p95 为 20.92／31.28 ms。压力档仍有提交间隔尖峰，不能据此声称稳定 60 FPS。缓存等待队列峰值均为 8（上限行为另由预算测试覆盖），关闭后无持续绘制或残留工作线程。数字来自一轮小片源回归，不与优化前非受控运行作性能提升百分比比较。

普通影片下载约 3,216 条弹幕；密集回放约 6,627 条、对应区间约 1,377 条候选，输入来自另一作品，仅作负载测试，不代表匹配准确。两轮仍播放同一 DM-V1 片段。两轮 UI 呈现历史覆盖均约 300 秒，未再捕获多秒停更；普通档仍有一段约 157–160 秒处的长帧簇，其原因尚未定位，不应声称完全无卡顿。HWUI 耗时 p95 分别 14.03／21.18 ms，超过 16.7 ms 的工作帧占 3.21%／9.51%，与 SF 呈现间隔是不同指标。

测试结束后，设备服务器会话、全部原设置、轨道记忆与测试影片的观看位置／次数均与测试前一致，测试播放已释放。私有片源、账户、原始日志和截图不提交。当前结论为：本设备 4K SDR 播放没有观察到弹幕导致的视频丢帧或缓冲，少量档开销较低；密集弹幕仍增加 UI 长帧，建议保留“少量＋自动减少”。这不是所有低端盒子、4K HDR、双字幕或全片长时间运行的验收。


### 2026-11-02 搜索空闲连接恢复

在 API 31 ARM64 TV 模拟器上复现：同词连续搜索正常，空闲 6 秒后的请求约 30 ms 即以 `CONNECTION / IOException` 失败，下一次搜索成功；6 次中成功 5 次。网络记录显示复用了连接，但失败前没有收到响应头，符合服务端关闭空闲连接后的恢复缺失。此前来源客户端和 Transport 均强制关闭了连接失败重试。
